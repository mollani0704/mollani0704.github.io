## 1. useEffect의 본래 역할

많은 개발자가 `useEffect`를 "렌더링 후 실행되는 함수" 정도로 이해한다. 이 설명이 완전히 틀린 것은 아니지만, 그것만으로는 부족하다. 더 정확히 말하면 `useEffect`는 **렌더링 이후 React 바깥의 시스템과 컴포넌트를 맞춰 주는 장치**이다. 예를 들어 네트워크 연결, 브라우저 이벤트 구독, 타이머, DOM API, 서드파티 라이브러리 제어 같은 작업이 이에 해당한다. React 공식 문서는 이러한 외부 시스템과의 연결이 `useEffect`의 핵심 사용처라고 설명한다.

즉, `useEffect`는 단순히 "렌더가 끝났으니 뭔가 해도 되는 곳"이 아니다. 오히려 "React 내부 계산만으로 해결되지 않는 일을 처리하는 곳"이라고 이해하는 편이 정확하다. 이 관점으로 보면, 값 계산, 상태 변환, 사용자 클릭 후 처리, 부모에게 데이터 전달 같은 일은 `useEffect`보다 다른 방식으로 해결해야 하는 경우가 많다.

## 2. 왜 useEffect를 남용하면 문제가 되는가

React 공식 문서는 불필요한 Effect를 제거하면 코드가 더 단순해지고, 더 빠르게 실행되며, 오류 가능성도 줄어든다고 설명한다. 특히 "외부 시스템이 없는 경우"에 상태를 Effect로 갱신하면, React는 한 번 렌더하고, DOM을 반영하고, Effect를 실행한 다음, 다시 상태 변경 때문에 또 렌더하게 된다. 이는 같은 결과를 얻기 위해 쓸데없이 한 번 더 렌더하는 셈이다. React의 lint 문서도 Effect 안에서 즉시 상태를 바꾸는 패턴이 전체 렌더 사이클을 다시 시작하게 만들어 성능 저하와 시각적 끊김을 유발할 수 있다고 경고한다.

해당 글에서도 이 점을 아주 구체적으로 보여 준다. 자식 컴포넌트가 클릭으로 자신의 상태를 바꾸고, 그 상태 변화를 Effect가 감지해서 부모의 `onChange`를 호출하면, 클릭 한 번에 로컬 상태 업데이트 렌더가 한 번 일어나고, 이어서 부모 상태 업데이트로 또 렌더가 발생한다. 즉, 로직이 늦게 따라오면서 렌더가 더 생긴다. 이는 사용자 이벤트를 이벤트 핸들러에서 바로 처리하지 않고, "상태 변경 후 Effect가 나중에 처리하는 구조"로 만들었기 때문에 생기는 문제다.

## useEffect를 쓰지 말아야 하는 대표적인 경우

### 1. props나 state로부터 계산 가능한 값을 다시 state에 넣는 경우

가장 흔한 남용 패턴은 "이미 가지고 있는 값들로 계산 가능한 결과를 굳이 state로 또 저장하는 경우"이다. 예를 들어 `firstName`과 `lastName`이 있을 때 `fullName`을 Effect로 계산해서 상태에 넣는 방식이다. React 공식 문서는 이런 경우 `fullName`은 상태가 아니라 렌더 중 계산해야 한다고 설명한다. 계산 가능한 값을 state로 만들면 불필요한 Effect와 추가 렌더가 생기고, 여러 상태 사이의 동기화 오류 가능성도 커진다.

나쁜 예시는 다음과 같다.

```jsx
import { useEffect, useState } from 'react';

function UserProfileForm() {
  const [firstName, setFirstName] = useState('Jongseong');
  const [lastName, setLastName] = useState('Moon');
  const [fullName, setFullName] = useState('');

  useEffect(() => {
    setFullName(`${firstName} ${lastName}`);
  }, [firstName, lastName]);

  return (
    <div>
      <input
        value={firstName}
        onChange={(e) => setFirstName(e.target.value)}
        placeholder="이름"
      />
      <input
        value={lastName}
        onChange={(e) => setLastName(e.target.value)}
        placeholder="성"
      />
      <p>전체 이름: {fullName}</p>
    </div>
  );
}
```

이 코드는 얼핏 자연스러워 보이지만, 사실 `fullName`은 `firstName`과 `lastName`으로부터 언제든 계산할 수 있다. 따라서 state로 따로 보관할 필요가 없다. 이 방식은 최초 렌더 시 빈 문자열로 한 번 화면이 계산되고, 이후 Effect가 실행되며 다시 `fullName`을 넣고 재렌더하는 흐름을 만든다. React 공식 문서는 이런 패턴을 불필요하고 비효율적이라고 본다.

좋은 예시는 다음과 같다.

```jsx
import { useState } from 'react';

function UserProfileForm() {
  const [firstName, setFirstName] = useState('Jongseong');
  const [lastName, setLastName] = useState('Moon');

  const fullName = `${firstName} ${lastName}`;

  return (
    <div>
      <input
        value={firstName}
        onChange={(e) => setFirstName(e.target.value)}
        placeholder="이름"
      />
      <input
        value={lastName}
        onChange={(e) => setLastName(e.target.value)}
        placeholder="성"
      />
      <p>전체 이름: {fullName}</p>
    </div>
  );
}
```

이 구조가 더 좋은 이유는 간단하다. `fullName`은 데이터의 "결과"이지 "독립적으로 관리해야 하는 상태"가 아니기 때문이다. 렌더링 중 계산하면 React의 데이터 흐름이 단순해지고, 불필요한 Effect와 추가 렌더도 없어진다.

### 2. 렌더링용 데이터 가공을 Effect로 처리하는 경우

리스트 필터링이나 정렬도 비슷하다. 예를 들어 `items`가 바뀔 때마다 `useEffect` 안에서 `setFilteredItems(...)`를 호출하는 패턴은 많이 보이지만, React 공식 문서는 이런 데이터 변환은 렌더링 단계에서 직접 처리하라고 권장한다. Effect는 외부 시스템과의 동기화용이지, 화면에 보여 줄 값을 가공하는 용도가 아니다.

나쁜 예시는 아래와 같다.

```jsx
import { useEffect, useState } from 'react';

function ProductList({ products, keyword }) {
  const [filteredProducts, setFilteredProducts] = useState([]);

  useEffect(() => {
    const next = products.filter((product) =>
      product.name.toLowerCase().includes(keyword.toLowerCase())
    );
    setFilteredProducts(next);
  }, [products, keyword]);

  return (
    <ul>
      {filteredProducts.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

좋은 예시는 다음과 같다.

```jsx
function ProductList({ products, keyword }) {
  const filteredProducts = products.filter((product) =>
    product.name.toLowerCase().includes(keyword.toLowerCase())
  );

  return (
    <ul>
      {filteredProducts.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

이처럼 렌더링에 필요한 값은 가급적 렌더 중 계산하는 것이 좋다. 계산 비용이 매우 크다면 `useMemo`를 고려할 수 있지만, 그 경우에도 핵심은 "Effect로 상태를 하나 더 만들지 않는다"는 점이다.

### 3. 사용자 이벤트를 Effect로 처리하는 경우

React 공식 문서는 "사용자 이벤트를 처리하기 위해 Effect가 필요하지 않다"고 분명히 설명한다. 버튼을 눌렀을 때 API를 호출하거나 알림을 띄우는 일은 클릭 이벤트 핸들러에서 하면 된다. 사용자가 무엇을 했는지는 이벤트 핸들러 시점에서 가장 정확하게 알 수 있기 때문이다. 반면 Effect는 렌더 이후에 실행되므로, "왜 이 Effect가 실행되었는가"를 추적해야 하는 추가 부담이 생긴다.

나쁜 예시는 다음과 같다.

```jsx
import { useEffect, useState } from 'react';

function PurchaseButton() {
  const [shouldBuy, setShouldBuy] = useState(false);

  useEffect(() => {
    if (!shouldBuy) return;

    async function buy() {
      await fetch('/api/buy', { method: 'POST' });
      alert('구매가 완료되었습니다.');
    }

    buy();
  }, [shouldBuy]);

  return <button onClick={() => setShouldBuy(true)}>구매하기</button>;
}
```

이 코드는 "클릭 -> 상태 변경 -> 렌더 -> Effect 실행 -> API 호출"이라는 우회 경로를 만든다. 클릭하면 바로 처리할 수 있는 일을 굳이 상태와 Effect를 통해 한 단계 돌아가고 있는 셈이다. React 공식 문서는 이런 경우를 Effect가 필요 없는 대표 사례로 든다.

좋은 예시는 다음과 같다.

```jsx
function PurchaseButton() {
  const handleBuy = async () => {
    await fetch('/api/buy', { method: 'POST' });
    alert('구매가 완료되었습니다.');
  };

  return <button onClick={handleBuy}>구매하기</button>;
}
```

### 4. 자식에서 Effect로 부모 상태를 밀어 올리는 경우

원문 글에서 특히 강조하는 부분 중 하나는 데이터 흐름 방향이다. React의 데이터는 일반적으로 부모에서 자식으로 흐르는 것이 자연스럽다. 그런데 자식이 데이터를 가져온 뒤, Effect에서 부모의 콜백을 호출하여 부모 상태를 다시 갱신하는 구조는 데이터 흐름을 꼬이게 만든다. 글에서는 이런 패턴이 "진실의 출처"를 흐리게 하고, 유지보수와 디버깅을 어렵게 만든다고 지적한다.

나쁜 예시는 다음과 같다.

```jsx
import { useEffect, useState } from 'react';

function Parent() {
  const [user, setUser] = useState(null);

  return <Child onFetched={setUser} />;
}

function Child({ onFetched }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    async function fetchUser() {
      const response = await fetch('/api/user');
      const result = await response.json();
      setData(result);
    }

    fetchUser();
  }, []);

  useEffect(() => {
    if (data) {
      onFetched(data);
    }
  }, [data, onFetched]);

  return <div>{data ? data.name : '로딩 중...'}</div>;
}
```

이 구조에서는 자식이 데이터를 들고 있다가, 다시 Effect를 통해 부모에게 전달한다. 즉, 데이터의 출처가 자식인지 부모인지 흐릿해진다. 또한 자식의 상태 변경으로 렌더가 일어나고, 그 뒤 부모 상태 변경으로 다시 렌더가 이어진다. 원문 글은 이런 구조를 피하고, 가능하면 부모가 상태를 직접 소유하도록 하라고 제안한다.

더 좋은 예시는 아래와 같다.

```jsx
import { useEffect, useState } from 'react';

function Parent() {
  const [user, setUser] = useState(null);

  useEffect(() => {
    let ignore = false;

    async function fetchUser() {
      const response = await fetch('/api/user');
      const result = await response.json();

      if (!ignore) {
        setUser(result);
      }
    }

    fetchUser();

    return () => {
      ignore = true;
    };
  }, []);

  return <Child user={user} />;
}

function Child({ user }) {
  if (!user) {
    return <div>로딩 중...</div>;
  }

  return <div>{user.name}</div>;
}
```

이 구조에서는 데이터의 출처가 부모에 명확히 있다. 자식은 단지 전달받아 표시할 뿐이다. React에서 상태의 소유권이 분명할수록 코드의 이해와 유지보수가 쉬워진다.

## useEffect를 써야 하는 경우

### 1. 외부 시스템과 연결할 때

React 공식 문서는 `useEffect`의 대표적인 용도를 네트워크 연결, 전역 이벤트 구독, 타이머, 애니메이션 라이브러리, 모달 제어 등으로 제시한다. 공통점은 모두 React가 직접 관리하지 않는 대상과 연결된다는 점이다. 이런 경우에는 렌더링만으로 원하는 동작을 만들 수 없기 때문에 Effect가 필요하다.

예를 들어 브라우저 이벤트 구독은 전형적인 Effect 사용 사례이다.

```jsx
import { useEffect, useState } from 'react';

function WindowWidthViewer() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }

    window.addEventListener('resize', handleResize);

    return () => {
      window.removeEventListener('resize', handleResize);
    };
  }, []);

  return <p>현재 창 너비: {width}px</p>;
}
```

이 예제에서 `window`는 React가 관리하는 값이 아니다. 따라서 컴포넌트가 화면에 있는 동안 `resize` 이벤트를 구독하고, 사라질 때 정리하는 과정이 필요하다. 이런 작업은 Effect가 정확한 도구이다.

### 2. 타이머를 등록하고 해제할 때

타이머 역시 React 외부의 시스템이다. `setInterval`, `setTimeout` 같은 브라우저 API는 렌더링과 별개로 동작하므로, 컴포넌트의 생명주기에 맞춰 등록과 해제를 관리해야 한다. React 공식 문서도 타이머를 Effect의 대표 예시로 든다.

```jsx
import { useEffect, useState } from 'react';

function Clock() {
  const [time, setTime] = useState(new Date());

  useEffect(() => {
    const timerId = setInterval(() => {
      setTime(new Date());
    }, 1000);

    return () => {
      clearInterval(timerId);
    };
  }, []);

  return <p>{time.toLocaleTimeString()}</p>;
}
```

여기서는 컴포넌트가 마운트되면 타이머를 시작하고, 언마운트되면 정리한다. 이처럼 "설치와 해제"가 짝을 이루는 구조는 `useEffect`의 전형적인 형태이다.

### 3. 외부 라이브러리나 DOM을 제어할 때

React 바깥에서 동작하는 위젯, 차트, 애니메이션, 지도 라이브러리 같은 것들은 React 상태가 바뀌었다고 자동으로 동기화되지 않는다. 이때는 Effect에서 해당 라이브러리의 API를 호출해 React 상태를 반영해야 한다. React 공식 문서도 비 React 위젯 제어를 `useEffect` 사용 예시로 소개한다.

```jsx
import { useEffect, useRef } from 'react';

function VideoPlayer({ isPlaying }) {
  const videoRef = useRef(null);

  useEffect(() => {
    if (!videoRef.current) return;

    if (isPlaying) {
      videoRef.current.play();
    } else {
      videoRef.current.pause();
    }
  }, [isPlaying]);

  return <video ref={videoRef} width="400" src="/sample-video.mp4" controls />;
}
```

이 경우 `videoRef.current.play()`와 `pause()`는 DOM API 호출이며, React 렌더링만으로 자동 실행되지 않는다. 따라서 `isPlaying` 상태와 실제 비디오 재생 상태를 동기화하기 위해 Effect가 필요하다.

## 네트워크 호출은 언제 useEffect를 써야 하는가

많은 초보 개발자가 가장 헷갈리는 부분이 바로 이것이다. 네트워크 요청은 외부 시스템과의 통신이므로, 원칙적으로는 `useEffect` 사용 대상이 맞다. React 공식 문서도 검색어와 검색 결과를 동기화하는 예시처럼 데이터 패칭에 Effect를 사용할 수 있다고 설명한다. 다만 현대 React에서는 프레임워크나 전용 데이터 패칭 도구가 더 효율적인 방법을 제공할 수 있다고 함께 언급한다.

즉, "API 호출 = 무조건 useEffect"라고 단정하기보다는 다음처럼 이해하는 것이 좋다.

첫째, 컴포넌트가 화면에 나타났을 때 데이터를 가져와야 한다면 Effect를 사용할 수 있다.

둘째, 하지만 취소 처리, 경쟁 상태, 캐싱, 재시도, 중복 요청 방지까지 직접 관리해야 하므로 생각보다 까다롭다.

셋째, 그래서 실무에서는 React Query 같은 서버 상태 라이브러리를 함께 사용하는 경우가 많다.

기본적인 데이터 패칭 예시는 다음과 같다.

```jsx
import { useEffect, useState } from 'react';

function UserDetail({ userId }) {
  const [user, setUser] = useState(null);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignore = false;

    async function fetchUser() {
      try {
        setIsLoading(true);
        setError(null);

        const response = await fetch(`/api/users/${userId}`);
        if (!response.ok) {
          throw new Error('사용자 정보를 불러오지 못했습니다.');
        }

        const result = await response.json();

        if (!ignore) {
          setUser(result);
        }
      } catch (err) {
        if (!ignore) {
          setError(err.message);
        }
      } finally {
        if (!ignore) {
          setIsLoading(false);
        }
      }
    }

    fetchUser();

    return () => {
      ignore = true;
    };
  }, [userId]);

  if (isLoading) {
    return <div>불러오는 중...</div>;
  }

  if (error) {
    return <div>에러: {error}</div>;
  }

  if (!user) {
    return null;
  }

  return (
    <section>
      <h2>{user.name}</h2>
      <p>{user.email}</p>
    </section>
  );
}
```

이 코드에서 중요한 부분은 cleanup이다. 원문 글은 경쟁 상태를 예로 들며, 이전 요청이 나중에 도착해 최신 데이터를 덮어쓰는 문제가 발생할 수 있음을 보여 준다. React 공식 문서 역시 cleanup 플래그를 통해 이전 요청의 결과를 무시하는 패턴을 안내한다. 즉, 데이터 패칭에서 Effect를 쓸 수는 있지만, 동시에 조심스럽게 다뤄야 한다.

## 원문 글이 특히 강조하는 핵심 포인트

### 1. 이벤트에서 처리할 수 있는 일은 이벤트에서 처리하라

자식 컴포넌트에서 클릭으로 상태를 바꾸고, 그 상태 변화를 Effect가 감지해 부모에게 알리는 방식은 비효율적이다. 글은 이런 구조가 렌더를 한 번 더 만들기 때문에, 가능하면 이벤트 핸들러 안에서 필요한 상태 업데이트를 한 번에 처리하라고 제안한다. React 공식 문서도 사용자 이벤트는 해당 이벤트 핸들러에서 처리하는 것이 일반적이라고 설명한다.

```jsx
import { useState } from 'react';

function Parent() {
  const [enabled, setEnabled] = useState(false);

  return <ToggleButton onChange={setEnabled} value={enabled} />;
}

function ToggleButton({ value, onChange }) {
  const handleClick = () => {
    const nextValue = !value;
    onChange(nextValue);
  };

  return <button onClick={handleClick}>현재 상태: {value ? 'ON' : 'OFF'}</button>;
}
```

이 코드는 클릭이라는 사건이 발생했을 때 필요한 일을 바로 처리한다. 별도의 Effect가 필요 없다. 원인과 결과가 가까이 붙어 있으므로 읽기도 쉽다.

### 2. 데이터는 가능하면 위에서 아래로 흐르게 하라

원문 글은 "React의 데이터는 폭포수처럼 흘러야 한다"고 표현한다. 즉, 부모가 상태를 가지고 자식에게 전달하는 방향이 가장 자연스럽다. 자식이 데이터를 받아서 다시 Effect로 부모 상태를 건드리는 구조는 가능은 하지만, 코드가 복잡해지고 추적이 어려워진다. 상태의 소유권과 데이터의 진실의 출처가 어디인지 항상 명확해야 한다.

### 3. Effect 안의 setState는 특히 조심해야 한다

모든 Effect 안의 `setState`가 나쁜 것은 아니지만, "렌더링에 필요한 값을 다시 Effect 안에서 상태로 세팅하는 패턴"은 거의 항상 더 나은 대안이 있다. React의 lint 문서는 Effect 안의 즉시 상태 변경이 전체 렌더 사이클을 다시 시작시켜, 피할 수 있었던 추가 렌더를 만든다고 설명한다. 이 때문에 코드는 느려지고, 때로는 깜빡임이나 렌더 타이밍 문제까지 유발할 수 있다.

## useEffect를 판단하는 기준

실무에서 `useEffect`를 써야 할지 고민될 때는 다음 기준으로 생각하면 좋다.

첫 번째 질문은 이것이다.

**이 작업이 React 바깥의 무언가와 연결되는가?**

브라우저 API, 타이머, 네트워크, DOM, 서드파티 라이브러리와의 동기화라면 `useEffect` 후보가 된다.

두 번째 질문은 이것이다.

**이미 있는 props나 state로 그냥 계산 가능한가?**

그렇다면 Effect 대신 렌더 중 계산해야 한다. 공식 문서는 계산 가능한 값은 state에 넣지 말고 렌더링 중 계산하라고 말한다.

세 번째 질문은 이것이다.

**이 작업이 사용자 행동 때문에 일어나는가?**

클릭, 입력, 제출 때문에 해야 하는 일이라면 이벤트 핸들러에 두는 것이 보통 더 적절하다. React 공식 문서는 사용자 이벤트 처리를 Effect로 하지 말라고 설명한다.

## 정리

`useEffect`는 "렌더링 후에 아무 코드나 넣는 공간"이 아니다. 그것은 React의 선언적 데이터 흐름에서 잠시 벗어나, 외부 시스템과 컴포넌트를 연결하는 **탈출구**에 가깝다. React 공식 문서는 외부 시스템이 없다면 대개 Effect가 필요 없다고 설명하고, 원문 글도 불필요한 Effect가 경쟁 상태, 추가 렌더, 데이터 흐름 왜곡, 코드 복잡도를 유발한다고 경고한다.

따라서 다음처럼 기억하면 좋다.

렌더링에 필요한 값 계산은 렌더 중에 한다.

사용자 이벤트로 인한 작업은 이벤트 핸들러에서 처리한다.

외부 시스템과의 동기화만 `useEffect`에 맡긴다.
