## 서론

현대 프론트엔드 개발에서는 `import` / `export` 문법을 아주 자연스럽게 사용한다.

하지만 여기서 한 가지를 분리해서 이해할 필요가 있다.

- `import`, `export`, `require` 같은 것은 모듈 시스템의 문법과 규칙이다.
- 브라우저에서 이것들을 실제로 실행 가능하게 만들고 최적화하는 것은 번들러의 역할이다.

이 둘을 한 덩어리로 이해하면 "Webpack이 모듈 시스템을 지원한다" 정도로만 기억하게 되는데, 이 표현은 엄밀히 말하면 조금 부정확하다.

이 글에서는 자바스크립트의 대표적인 모듈 시스템인 CommonJS, AMD, ESM을 먼저 정리하고, Browserify와 Webpack 같은 번들러가 왜 필요했는지, 그리고 모듈 시스템과 번들러가 어떤 관계인지 차례대로 정리해보려고 한다.

## 모듈 시스템이란 무엇인가

모듈 시스템(Module System)은 코드를 여러 파일로 나누고, 필요한 코드를 다른 파일에서 가져와 사용할 수 있도록 하는 규칙이다.

즉, 다음 두 가지를 정의한다고 보면 된다.

- 코드를 어떻게 분리할 것인가
- 분리된 코드를 어떤 방식으로 불러올 것인가

이 관점에서 보면 모듈 시스템은 "코드 조직 규칙"에 가깝고, 번들러는 그 규칙을 해석해서 실제 실행 가능한 결과물을 만드는 도구에 가깝다.

## CommonJS

CommonJS는 주로 Node.js 환경에서 널리 사용된 모듈 시스템이다.

```jsx
const foo = require('./foo')
module.exports = bar
```

특징은 다음과 같다.

- `require()`로 모듈을 가져온다.
- `module.exports`로 외부에 내보낸다.
- 기본적으로 동기 방식으로 모듈을 로드한다.

이 방식은 서버 환경에서는 잘 맞는다. 필요한 파일을 로컬 파일 시스템에서 바로 읽어올 수 있기 때문이다.

반면 브라우저는 `require` 자체를 기본적으로 이해하지 못한다. 따라서 CommonJS 문법으로 작성된 코드는 브라우저에서 그대로 실행할 수 없다.

## AMD

AMD(Asynchronous Module Definition)는 브라우저 환경을 고려해 만들어진 모듈 시스템이다.

```jsx
define(['a', 'b'], function (a, b) {
  return {}
})
```

특징은 다음과 같다.

- 비동기 방식으로 모듈을 불러오는 데 초점이 있다.
- 브라우저에서 여러 스크립트를 관리하기 위한 목적이 강했다.
- 대표적으로 RequireJS 같은 도구와 함께 사용되었다.

당시에는 브라우저 환경에서 꽤 현실적인 대안이었지만, 문법이 다소 장황하고 개발 경험이 좋지 않은 편이었다. 결국 CommonJS, AMD, 이후의 ESM이 공존하면서 생태계가 분산되는 문제도 생겼다.

## ESM

ESM(ECMAScript Modules)은 자바스크립트 공식 표준 모듈 시스템이다.

```jsx
import { foo } from './foo'
export default bar
```

특징은 다음과 같다.

- 자바스크립트 언어 표준에 포함되어 있다.
- `import` / `export` 문법을 사용한다.
- 정적 분석이 가능하다.
- 브라우저와 서버 양쪽에서 사용할 수 있다.

ESM의 중요한 장점 중 하나는 정적 분석이 가능하다는 점이다. 어떤 모듈을 가져오는지 코드 실행 전에 파악할 수 있기 때문에, 트리 쉐이킹 같은 최적화에도 유리하다.

현재는 ESM이 사실상 표준으로 자리 잡았다고 봐도 무리가 없다.

## 번들러란 무엇인가

번들러(Bundler)는 여러 개의 모듈 파일을 읽고, 이들의 의존 관계를 분석한 뒤, 브라우저에서 실행 가능한 형태의 결과물로 변환하는 도구이다.

대표적인 도구는 다음과 같다.

- Browserify
- Webpack

번들러의 핵심 역할은 보통 아래와 같이 정리할 수 있다.

- 모듈 간 의존성 분석
- 브라우저가 이해할 수 있는 코드로 변환
- 여러 파일을 하나 또는 여러 개의 번들 파일로 구성
- 성능 최적화 적용

즉, 번들러는 단순히 파일을 합치는 도구가 아니라, 애플리케이션 전체 구조를 읽고 재구성하는 도구다.

## "지원"이 아니라 "해석과 변환"

번들러를 설명할 때 흔히 "Webpack이 CommonJS를 지원한다", "Webpack이 ESM을 지원한다"라고 말한다.

완전히 틀린 말은 아니지만, 더 정확한 표현은 다음에 가깝다.

> 번들러는 특정 모듈 시스템 문법을 해석하고, 브라우저에서 실행 가능한 코드로 변환한다.

예를 들어 브라우저는 아래 코드를 그대로 이해하지 못한다.

```jsx
const foo = require('./foo')
```

브라우저에는 Node.js의 `require` 런타임이 없기 때문이다.

이때 Browserify나 Webpack 같은 도구는 `require('./foo')`를 분석해서,

- 어떤 파일이 필요한지 찾고
- 의존성 관계를 그래프로 만들고
- 내부적인 로더 함수 형태로 감싸서
- 브라우저에서도 동작하도록 변환한다

즉, "지원"의 본질은 문법을 그대로 실행해주는 것이 아니라, 해석한 뒤 재구성하는 것이다.

ESM도 마찬가지다.

```jsx
import { foo } from './foo'
```

이 코드를 보고 번들러는 의존성을 수집하고, 최종 번들에 어떤 코드가 포함되어야 하는지 결정한다.

## 번들러의 핵심 개념: 의존성 그래프

번들러를 이해할 때 가장 중요한 개념 중 하나가 의존성 그래프(dependency graph)다.

예를 들어 엔트리 파일이 `index.js`이고, 그 안에서 다른 파일들을 불러온다고 해보자.

```txt
index.js
 ├── a.js
 │   └── c.js
 └── b.js
```

번들러는 이 구조를 따라가며 애플리케이션 전체의 연결 관계를 파악한다.

그리고 이 그래프를 기반으로

- 어떤 파일이 실제로 필요한지
- 어떤 순서로 실행되어야 하는지
- 어떤 코드를 별도 청크로 분리할지

를 결정한다.

즉, 번들러는 파일 하나만 보는 것이 아니라 프로젝트 전체를 하나의 그래프로 바라본다.

## 번들링은 단순히 "하나로 합치기"가 아니다

초기 번들러의 이미지는 "여러 파일을 하나의 파일로 묶는 도구"에 가까웠다.

물론 이것도 맞는 설명이지만, 현대 번들러는 그보다 훨씬 많은 일을 한다.

### 코드 스플리팅

필요한 코드를 한 번에 전부 내려보내는 대신, 여러 개의 청크로 나눠서 필요한 시점에만 로드할 수 있다.

예를 들면 다음과 같다.

```txt
main.js
vendors.js
lazy-chunk.js
```

이렇게 하면 초기 로딩에 꼭 필요한 코드만 먼저 불러오고, 나머지는 나중에 받아올 수 있다.

결과적으로 초기 로딩 성능이 좋아질 수 있다.

### 트리 쉐이킹

번들러는 사용되지 않는 코드를 제거할 수 있다.

예를 들어 어떤 모듈에서 함수 10개를 내보내더라도, 실제로 2개만 사용한다면 나머지를 번들 결과물에서 제외할 수 있다.

이 최적화는 특히 ESM의 정적 분석 특성과 잘 맞는다.

### 기타 최적화

현대 번들러는 보통 다음과 같은 추가 작업도 함께 수행한다.

- 압축(minification)
- 캐싱 전략을 고려한 파일명 분리
- CSS, 이미지, 폰트 같은 자산 처리
- 개발 서버와 HMR 같은 개발 편의 기능 제공

그래서 오늘날 번들러는 단순 변환기라기보다, 프론트엔드 빌드 파이프라인의 중심 도구로 이해하는 편이 더 정확하다.

## 모듈 시스템과 번들러의 관계

지금까지의 내용을 역할 기준으로 다시 정리하면 다음과 같다.

### 모듈 시스템

- 코드를 나누는 규칙이다.
- 모듈을 가져오고 내보내는 문법을 정의한다.
- 대표적으로 CommonJS, AMD, ESM이 있다.

### 번들러

- 모듈 문법을 해석한다.
- 의존성 그래프를 만든다.
- 브라우저에서 실행 가능한 코드로 변환한다.
- 성능 최적화를 적용한다.

즉, 모듈 시스템은 "규칙"이고, 번들러는 그 규칙을 이용해 "실행 가능한 결과물"을 만드는 도구다.

## ESM 시대에도 번들러가 필요한 이유

지금은 브라우저도 ESM을 직접 지원한다.

그래서 겉보기에는 "이제 번들러가 필요 없는 것 아닌가?"라는 질문이 자연스럽다.

하지만 실제 서비스에서는 여전히 번들러가 중요한 경우가 많다.

그 이유는 다음과 같다.

- 초기 로딩 성능 최적화가 필요하다.
- 네트워크 요청 수를 조절해야 한다.
- 코드 스플리팅과 캐싱 전략이 중요하다.
- CSS, 이미지, 폰트 등 다양한 자산을 함께 처리해야 한다.
- 개발 환경에서 빠른 피드백과 편의 기능이 필요하다.

즉, ESM의 표준화가 번들러를 완전히 대체한 것은 아니다. 오히려 번들러의 역할이 "모듈을 억지로 실행하게 만드는 도구"에서 "최적화와 빌드 orchestration 도구"로 더 분명해졌다고 보는 편이 맞다.

## 결론

자바스크립트 생태계에서 모듈 시스템과 번들러는 서로 다른 문제를 해결한다.

모듈 시스템은 코드를 어떻게 나누고 연결할지에 대한 규칙이고, 번들러는 그 규칙을 해석해서 실제 배포 가능한 결과물로 만드는 도구다.

핵심만 다시 정리하면 다음과 같다.

- CommonJS, AMD, ESM은 모듈을 정의하고 불러오는 방식이다.
- Browserify와 Webpack은 이런 모듈을 분석하고 변환하는 도구다.
- 번들러의 본질은 단순 지원이 아니라 해석과 변환이다.
- 현대에는 ESM이 표준이지만, 번들러는 여전히 최적화의 중심 역할을 한다.

이 구분을 명확히 해두면, 프론트엔드 빌드 도구를 공부할 때도 "문법"과 "도구"를 분리해서 더 정확하게 이해할 수 있다.
