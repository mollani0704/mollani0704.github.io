Redux를 처음 접하면 가장 자주 듣는 말 중 하나가 있다.

> "기존 state를 직접 변경하지 말고, 반드시 새로운 객체를 만들어서 업데이트해야 한다."

처음에는 이 말이 단순한 문법 규칙처럼 들릴 수 있다. 하지만 이 원칙은 Redux만의 취향이 아니다. JavaScript가 값을 저장하고 비교하는 방식, 그리고 Redux가 상태 변화를 추적하는 방식 때문에 반드시 지켜야 하는 핵심 규칙이다.

이번 글에서는 JavaScript의 **원시값(Primitive)** 과 **참조값(Reference Type)** 의 차이부터 시작해서, 왜 Redux에서 **불변성(Immutability)** 이 중요한지 구조적으로 정리해본다.

## 1. JavaScript 값의 두 가지 종류

JavaScript에서 값은 크게 두 가지로 나뉜다.

- 원시값(Primitive)
- 참조값(Reference Type)

이 둘의 차이를 이해해야 Redux의 불변성도 자연스럽게 이해된다.

## 2. 원시값은 값 자체가 복사된다

원시값에는 보통 다음이 포함된다.

- `number`
- `string`
- `boolean`
- `null`
- `undefined`
- `symbol`
- `bigint`

원시값은 변수에 **값 자체가 저장**된다.

```js
let a = 10
let b = a

console.log(a) // 10
console.log(b) // 10
console.log(a === b) // true
```

여기서 `b = a`는 `a`가 들고 있던 숫자 `10`을 그대로 복사한 것이다.

이후 `b`를 바꿔도 `a`에는 아무 영향이 없다.

```js
let a = 10
let b = a

b = 20

console.log(a) // 10
console.log(b) // 20
```

즉, 원시값은 복사 이후 서로 완전히 독립적이다.

## 3. 참조값은 주소가 복사된다

반면 객체와 배열은 다르게 동작한다.

- `object`
- `array`

이 값들은 변수에 **값 자체가 저장되는 것이 아니라, 해당 값을 가리키는 참조(주소)** 가 저장된다.

예를 보자.

```js
const person = {
  name: 'Max',
}

const newPerson = person

console.log(person === newPerson) // true
```

여기서 `newPerson = person`은 객체를 새로 복사한 것이 아니다. 같은 객체를 가리키는 주소를 하나 더 만든 것이다.

그래서 한쪽에서 수정하면 다른 쪽에서도 그 변경이 보인다.

```js
const person = {
  name: 'Max',
}

const newPerson = person

newPerson.name = 'Anna'

console.log(person.name) // Anna
console.log(newPerson.name) // Anna
```

많은 초보자가 여기서 놀란다.

`newPerson`만 바꿨는데 왜 `person`도 바뀔까?

이유는 간단하다. 둘이 서로 다른 객체가 아니라 **같은 객체 하나를 함께 가리키고 있기 때문**이다.

## 4. 주소를 복사했다는 뜻을 그림으로 보면 더 쉽다

아래처럼 생각하면 이해가 쉽다.

```txt
person -----> { name: 'Max' }
newPerson --> { name: 'Max' }
```

실제로는 이런 상태다.

```txt
person -----> [ 같은 객체 ]
newPerson --> [ 같은 객체 ]
```

변수는 상자 자체가 아니라 상자의 위치가 적힌 쪽지를 들고 있다고 생각하면 된다.

- 객체는 상자
- 변수는 그 상자의 주소가 적힌 쪽지

쪽지를 하나 더 복사했다고 해서 상자가 새로 생기지는 않는다.

그래서 상자 안을 바꾸면 두 변수 모두 같은 변화를 보게 된다.

## 5. 배열도 완전히 같다

배열도 객체이기 때문에 동일한 문제가 생긴다.

```js
const hobbies = ['Sports', 'Cooking']
const copiedHobbies = hobbies

copiedHobbies.push('Music')

console.log(hobbies) // ['Sports', 'Cooking', 'Music']
console.log(copiedHobbies) // ['Sports', 'Cooking', 'Music']
console.log(hobbies === copiedHobbies) // true
```

`push()`는 기존 배열 자체를 수정하는 메서드다. 따라서 `copiedHobbies`만 바꾼 것처럼 보여도 실제로는 원본 배열도 함께 바뀐다.

다음 메서드들은 특히 "기존 배열을 직접 바꾸는 메서드"라는 점을 기억해두면 좋다.

```js
const arr = [1, 2, 3]

arr.push(4) // 직접 수정
arr.pop() // 직접 수정
arr.splice(1, 1) // 직접 수정
arr.sort() // 직접 수정
arr.reverse() // 직접 수정
```

반면 이런 방식은 새 배열을 만든다.

```js
const arr = [1, 2, 3]

const next1 = [...arr, 4]
const next2 = arr.filter((item) => item !== 2)
const next3 = arr.map((item) => item * 2)

console.log(arr) // [1, 2, 3]
console.log(next1) // [1, 2, 3, 4]
console.log(next2) // [1, 3]
console.log(next3) // [2, 4, 6]
```

## 6. Redux는 왜 이 차이에 민감할까?

Redux는 상태를 이렇게 다룬다.

```txt
이전 상태(prev state) -> 액션(action) -> 다음 상태(next state)
```

이 구조의 핵심은 **이전 상태와 다음 상태를 명확히 구분하는 것**이다.

이 구분이 가능해야 다음이 쉬워진다.

- 어떤 값이 바뀌었는지 추적할 수 있다.
- 디버깅이 쉬워진다.
- 상태 흐름이 예측 가능해진다.
- React가 변경 여부를 빠르게 판단할 수 있다.

즉, Redux는 "상태를 그냥 저장하는 도구"가 아니라, **상태 변화 자체를 관리하는 도구**에 가깝다.

## 7. 기존 state를 직접 변경하면 실제로 무슨 일이 생길까?

가장 단순한 예부터 보자.

```js
const state = {
  counter: 0,
}

const nextState = state

nextState.counter = 1

console.log(state.counter) // 1
console.log(nextState.counter) // 1
console.log(state === nextState) // true
```

겉보기에는 `nextState`를 바꾼 것 같지만, 실제로는 기존 `state`도 함께 오염되었다.

즉, 아래 두 개가 따로 존재하는 것이 아니다.

```txt
prevState
nextState
```

실제로는 **둘 다 같은 객체 하나**다.

## 8. 문제 1: 이전 상태를 보존할 수 없다

Redux는 보통 "이전 상태와 비교해서 무엇이 바뀌었는지"를 기준으로 동작한다.

그런데 직접 수정하면 이전 상태가 그대로 남아있지 않는다.

```js
const prevState = {
  user: {
    name: 'Max',
  },
}

const nextState = prevState

nextState.user.name = 'Anna'

console.log(prevState.user.name) // Anna
```

`prevState`는 더 이상 이전 상태가 아니다. 이미 바뀌어버렸다.

그러면 이런 질문에 답하기가 어려워진다.

- 정확히 언제 바뀌었는가?
- 어느 reducer에서 바뀌었는가?
- 어떤 액션 때문에 바뀌었는가?

## 9. 문제 2: 참조 비교로는 변경을 감지할 수 없다

React와 Redux는 성능을 위해 **참조 비교(reference equality)** 를 자주 활용한다.

예를 들어 다음과 같은 비교가 자주 일어난다.

```js
if (prevState === nextState) {
  console.log('상태 변경 없음')
} else {
  console.log('상태 변경 있음')
}
```

이 비교는 "겉 객체가 새로 만들어졌는가?"를 보는 것이다.

그런데 직접 수정하면 내부 값은 바뀌어도 참조는 그대로다.

```js
const prevState = {
  counter: 0,
}

const nextState = prevState

nextState.counter = 1

console.log(prevState === nextState) // true
```

즉, 내부 값은 바뀌었는데도 바깥에서는 "같은 객체"로 보인다.

이런 상황은 Redux 입장에서 매우 위험하다. 상태가 바뀌었는데도 안 바뀐 것처럼 보일 수 있기 때문이다.

## 10. 문제 3: React 렌더링 최적화와도 충돌한다

React는 props나 state 변경 여부를 확인할 때 참조 비교에 많이 의존한다. 예를 들어 `React.memo`, `useSelector`, `useMemo`의 의존성 비교 같은 곳에서 이 개념이 중요하다.

예를 보자.

```js
const prev = {
  todos: ['Redux 공부'],
}

const next = prev

next.todos.push('불변성 이해하기')

console.log(prev === next) // true
```

이 경우 내부 배열은 바뀌었지만 최상위 객체는 동일하다. 그러면 일부 최적화 로직은 "변경 없음"으로 판단할 여지가 생긴다.

간단히 비유하면 이렇다.

- Redux와 React는 택배 상자의 바깥 송장 번호를 먼저 본다.
- 송장 번호가 같으면 "같은 상자네?"라고 빠르게 판단한다.
- 그런데 상자 안 물건만 몰래 바꿔버리면 바깥에서는 변화를 놓칠 수 있다.

## 11. 문제 4: 디버깅이 어려워진다

직접 수정은 버그를 만든 뒤 원인을 흐리게 만든다.

예를 들어 이런 reducer는 매우 위험하다.

```js
function reducer(state, action) {
  if (action.type === 'increment') {
    state.count += 1
    return state
  }

  return state
}
```

겉보기에는 별문제 없어 보이지만, 사실상 원본 state를 직접 수정하고 있다.

이런 코드는 다음 문제를 만든다.

- Redux DevTools로 흐름을 추적하기가 어려워진다.
- 어느 시점에서 값이 바뀌었는지 파악하기 어렵다.
- 동일한 입력에 동일한 결과가 나와야 하는 reducer의 예측 가능성이 깨진다.

Redux reducer는 본질적으로 **순수 함수처럼 동작해야 한다.**

```js
function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return {
        ...state,
        count: state.count + 1,
      }
    default:
      return state
  }
}
```

이런 형태여야 입력과 출력이 분명해진다.

## 12. Redux에서 원하는 상태 업데이트 방식

Redux는 상태 변화를 이런 식으로 표현하길 원한다.

```js
const oldState = {
  counter: 0,
}

const newState = {
  ...oldState,
  counter: 1,
}

console.log(oldState.counter) // 0
console.log(newState.counter) // 1
console.log(oldState === newState) // false
```

이 방식의 장점은 명확하다.

- 이전 상태가 보존된다.
- 새로운 상태가 따로 생성된다.
- 참조가 바뀌므로 변경 감지가 쉬워진다.

즉, Redux가 원하는 것은 "기존 값을 몰래 고치는 것"이 아니라, **이전 상태를 기반으로 다음 상태를 새로 만드는 것**이다.

## 13. 잘못된 업데이트 vs 올바른 업데이트

### 13-1. 객체 업데이트

잘못된 방식:

```js
function reducer(state, action) {
  state.user.name = action.payload
  return state
}
```

올바른 방식:

```js
function reducer(state, action) {
  return {
    ...state,
    user: {
      ...state.user,
      name: action.payload,
    },
  }
}
```

조금 더 실제적인 예도 보자.

```js
const state = {
  user: {
    id: 1,
    name: 'Max',
    age: 20,
  },
  isLoggedIn: true,
}

const nextState = {
  ...state,
  user: {
    ...state.user,
    age: 21,
  },
}

console.log(state.user.age) // 20
console.log(nextState.user.age) // 21
console.log(state === nextState) // false
console.log(state.user === nextState.user) // false
```

### 13-2. 배열 추가

잘못된 방식:

```js
function reducer(state, action) {
  state.items.push(action.payload)
  return state
}
```

올바른 방식:

```js
function reducer(state, action) {
  return {
    ...state,
    items: [...state.items, action.payload],
  }
}
```

예제:

```js
const state = {
  items: ['apple', 'banana'],
}

const nextState = {
  ...state,
  items: [...state.items, 'orange'],
}

console.log(state.items) // ['apple', 'banana']
console.log(nextState.items) // ['apple', 'banana', 'orange']
console.log(state.items === nextState.items) // false
```

### 13-3. 배열 삭제

잘못된 방식:

```js
function reducer(state, action) {
  state.items.splice(action.payload, 1)
  return state
}
```

올바른 방식:

```js
function reducer(state, action) {
  return {
    ...state,
    items: state.items.filter((_, index) => index !== action.payload),
  }
}
```

### 13-4. 배열 내부 객체 수정

실무에서 가장 자주 헷갈리는 패턴 중 하나다.

잘못된 방식:

```js
function reducer(state, action) {
  const todo = state.todos.find((todo) => todo.id === action.payload)
  todo.done = true
  return state
}
```

올바른 방식:

```js
function reducer(state, action) {
  return {
    ...state,
    todos: state.todos.map((todo) =>
      todo.id === action.payload ? { ...todo, done: true } : todo
    ),
  }
}
```

예제:

```js
const state = {
  todos: [
    { id: 1, text: 'Redux 공부', done: false },
    { id: 2, text: 'React 복습', done: false },
  ],
}

const nextState = {
  ...state,
  todos: state.todos.map((todo) =>
    todo.id === 1 ? { ...todo, done: true } : todo
  ),
}

console.log(state.todos[0].done) // false
console.log(nextState.todos[0].done) // true
console.log(state.todos === nextState.todos) // false
console.log(state.todos[0] === nextState.todos[0]) // false
console.log(state.todos[1] === nextState.todos[1]) // true
```

마지막 줄이 중요하다. 바뀐 항목만 새 객체가 되고, 나머지는 기존 참조를 재사용한다. 이런 방식이 불필요한 재생성을 줄이면서도 불변성을 유지하는 전형적인 패턴이다.

## 14. 얕은 복사(Shallow Copy)를 꼭 이해해야 한다

`spread` 문법은 편리하지만, **깊은 복사(deep copy)** 가 아니라 **얕은 복사(shallow copy)** 라는 점을 반드시 기억해야 한다.

예를 보자.

```js
const state = {
  user: {
    name: 'Max',
    address: {
      city: 'Seoul',
    },
  },
}

const newState = {
  ...state,
}

console.log(state === newState) // false
console.log(state.user === newState.user) // true
console.log(state.user.address === newState.user.address) // true
```

겉 객체는 새로 만들어졌지만 내부의 `user`, `address`는 그대로 같은 객체다.

따라서 아래 코드는 여전히 위험하다.

```js
const state = {
  user: {
    name: 'Max',
    address: {
      city: 'Seoul',
    },
  },
}

const newState = {
  ...state,
}

newState.user.address.city = 'Busan'

console.log(state.user.address.city) // Busan
```

겉만 복사하고 안쪽 객체는 공유하고 있기 때문이다.

### 중첩 객체는 변경되는 경로를 따라 단계별로 복사해야 한다

올바른 방식은 다음과 같다.

```js
const state = {
  user: {
    name: 'Max',
    address: {
      city: 'Seoul',
      zipCode: '12345',
    },
  },
}

const newState = {
  ...state,
  user: {
    ...state.user,
    address: {
      ...state.user.address,
      city: 'Busan',
    },
  },
}

console.log(state.user.address.city) // Seoul
console.log(newState.user.address.city) // Busan
console.log(state.user === newState.user) // false
console.log(state.user.address === newState.user.address) // false
```

핵심은 이거다.

- 바뀌는 위치까지의 경로를 따라 새 객체를 만들어야 한다.
- 안 바뀌는 나머지 값은 재사용해도 된다.

## 15. 흔히 하는 실수들

### 실수 1. 겉 객체만 복사하고 내부는 직접 수정하기

```js
const nextState = { ...state }
nextState.user.name = 'Anna'
```

이 코드는 안전해 보이지만 사실은 위험하다.

왜냐하면:

```js
console.log(state.user === nextState.user) // true
```

즉, 내부 `user` 객체는 그대로 공유된다.

### 실수 2. 배열만 복사하고 내부 객체는 직접 수정하기

```js
const nextTodos = [...state.todos]
nextTodos[0].done = true
```

이 역시 배열 껍데기만 새로 만들었을 뿐, 안의 객체는 그대로다.

```js
console.log(state.todos[0] === nextTodos[0]) // true
```

올바른 방식:

```js
const nextTodos = state.todos.map((todo, index) =>
  index === 0 ? { ...todo, done: true } : todo
)
```

### 실수 3. `sort()`를 안전하다고 착각하기

`sort()`는 새 배열을 반환하는 것처럼 보이지만 실제로는 기존 배열을 직접 바꾼다.

```js
const numbers = [3, 1, 2]
const sorted = numbers.sort()

console.log(numbers) // [1, 2, 3]
console.log(sorted) // [1, 2, 3]
console.log(numbers === sorted) // true
```

Redux state에 들어 있는 배열을 정렬해야 한다면 먼저 복사한 뒤 정렬해야 한다.

```js
const numbers = [3, 1, 2]
const sorted = [...numbers].sort()

console.log(numbers) // [3, 1, 2]
console.log(sorted) // [1, 2, 3]
console.log(numbers === sorted) // false
```

## 16. reducer가 순수해야 하는 이유

Redux reducer는 같은 입력이 들어오면 항상 같은 출력을 내야 한다.

예를 들어:

```js
const initialState = { count: 0 }
const action = { type: 'increment' }
```

이 입력으로 reducer를 호출했을 때 언제나 같은 결과가 나와야 한다.

좋은 reducer:

```js
function reducer(state = { count: 0 }, action) {
  switch (action.type) {
    case 'increment':
      return {
        ...state,
        count: state.count + 1,
      }
    default:
      return state
  }
}
```

나쁜 reducer:

```js
function reducer(state = { count: 0 }, action) {
  switch (action.type) {
    case 'increment':
      state.count += 1
      return state
    default:
      return state
  }
}
```

두 번째 코드는 "입력 객체 자체를 바꿔버리는 함수"라서 상태 추적이 어려워진다.

## 17. Redux Toolkit에서는 왜 직접 수정처럼 보여도 괜찮을까?

Redux Toolkit을 쓰면 이런 코드가 자주 나온다.

```js
const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1
    },
  },
})
```

이걸 보면 "방금까지 직접 수정하면 안 된다고 하지 않았나?"라는 생각이 든다.

이유는 **Immer** 때문이다.

Redux Toolkit은 내부적으로 Immer를 사용해서, 우리가 작성한 "수정처럼 보이는 코드"를 안전한 불변 업데이트로 변환한다.

개념적으로는 이런 느낌이다.

```js
// 우리가 작성하는 코드
state.value += 1
```

실제로 내부에서는 이런 결과를 만들어낸다.

```js
return {
  ...state,
  value: state.value + 1,
}
```

즉:

- 겉보기에는 mutate처럼 작성한다.
- 내부적으로는 새 state가 생성된다.
- 그래서 Redux의 불변성 규칙은 그대로 유지된다.

다만 중요한 점이 있다.

**Redux Toolkit이 Immer를 제공하기 때문에 가능한 것**이지, 일반 Redux reducer나 일반 JavaScript 객체에서 아무 때나 직접 수정해도 된다는 뜻은 아니다.

## 18. 실무 감각으로 정리하는 불변 업데이트 체크 포인트

Redux 코드를 쓸 때 아래 기준으로 빠르게 점검하면 도움이 된다.

### 이런 코드는 위험하다

```js
state.user.name = 'Anna'
state.items.push(newItem)
state.list.splice(0, 1)
state.todos[0].done = true
arr.sort()
```

공통점은 모두 **기존 값 자체를 직접 수정**한다는 점이다.

### 이런 코드는 안전하다

```js
return {
  ...state,
  user: {
    ...state.user,
    name: 'Anna',
  },
}
```

```js
return {
  ...state,
  items: [...state.items, newItem],
}
```

```js
return {
  ...state,
  todos: state.todos.map((todo) =>
    todo.id === id ? { ...todo, done: true } : todo
  ),
}
```

공통점은 모두 **새 객체 또는 새 배열을 만들어 반환**한다는 점이다.

## 19. 한 번에 감 잡는 비교 예제

### 원시값

```js
let x = 1
let y = x

y = 2

console.log(x) // 1
console.log(y) // 2
```

### 객체 참조

```js
const x = { value: 1 }
const y = x

y.value = 2

console.log(x.value) // 2
console.log(y.value) // 2
```

### 객체 불변 업데이트

```js
const x = { value: 1 }
const y = { ...x, value: 2 }

console.log(x.value) // 1
console.log(y.value) // 2
console.log(x === y) // false
```

### 배열 직접 수정

```js
const list = ['a', 'b']
const copied = list

copied.push('c')

console.log(list) // ['a', 'b', 'c']
```

### 배열 불변 업데이트

```js
const list = ['a', 'b']
const copied = [...list, 'c']

console.log(list) // ['a', 'b']
console.log(copied) // ['a', 'b', 'c']
```

## 20. 정리

Redux에서 기존 state를 직접 수정하면 안 되는 이유는 Redux가 까다로워서가 아니다. **JavaScript의 객체와 배열이 참조값이기 때문**이다.

핵심은 다음과 같다.

- 원시값은 값 자체가 복사된다.
- 객체와 배열은 참조가 복사된다.
- 그래서 직접 수정하면 기존 state도 함께 오염될 수 있다.
- Redux는 이전 상태와 다음 상태를 명확히 구분해야 한다.
- 참조가 바뀌어야 React와 Redux가 변경을 안정적으로 감지할 수 있다.
- `spread`는 얕은 복사이므로 중첩 객체는 단계별로 복사해야 한다.
- Redux Toolkit은 Immer 덕분에 mutate처럼 써도 내부적으로는 불변 업데이트가 수행된다.

한 문장으로 정리하면 이렇다.

> Redux에서 불변성이 중요한 이유는 객체와 배열이 참조값이기 때문에, 기존 state를 직접 수정하면 상태 변화 추적이 깨지고 예측 가능한 상태 관리가 어려워지기 때문이다.

불변성을 이해하면 Redux가 훨씬 덜 어렵게 느껴진다. 결국 Redux가 요구하는 것은 특별한 마법이 아니라, **JavaScript 객체와 배열이 어떻게 동작하는지 정확히 이해한 뒤 안전하게 상태를 다루는 습관**이기 때문이다.
