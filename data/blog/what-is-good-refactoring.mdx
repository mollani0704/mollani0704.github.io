리팩터링은 소프트웨어 개발에서 꼭 필요한 작업이다.  
하지만 모든 리팩터링이 좋은 결과를 만드는 것은 아니다. 잘못된 리팩터링은 코드의 가독성과 유지보수성을 떨어뜨리고, 성능 저하나 버그까지 유발할 수 있다.

좋은 리팩터링과 나쁜 리팩터링의 차이는 단순히 코드가 더 세련되어 보이는가에 있지 않다. 핵심은 **기존 동작을 유지하면서 코드베이스 전체의 이해 가능성과 유지보수성을 높였는가**에 있다.

![리팩터링의 두 얼굴](/static/images/refactoring_good_vs_bad_diagram.svg)

## 리팩터링의 목적은 스타일 변경이 아니라 구조 개선이다

많은 개발자가 리팩터링을 하면서 자신의 취향에 맞는 스타일이나 패러다임을 코드에 적용하고 싶어 한다. 예를 들어 평범한 반복문 기반 코드를 갑자기 함수형 스타일 중심으로 전환하는 경우가 있다. 이런 변화는 일부에게는 세련되어 보일 수 있지만, 팀 전체가 익숙하지 않다면 유지보수 비용만 커진다.

좋은 리팩터링은 기존 팀의 문맥 안에서 더 읽기 쉽고 자연스럽게 개선하는 것이다.

### 좋은 리팩터링 예시

```js
function getActiveUserNames(users) {
  const activeUserNames = []

  for (const user of users) {
    if (user.isActive) {
      activeUserNames.push(user.name)
    }
  }

  return activeUserNames
}
```

반복문 스타일을 유지하면서 변수명만 더 분명하게 다듬은 예시다. 팀이 이미 이런 스타일에 익숙하다면 충분히 좋은 개선이다.

### 나쁜 리팩터링 예시

```js
import { pipe, filter, map, prop } from 'ramda'

const getActiveUserNames = pipe(
  filter(prop('isActive')),
  map(prop('name'))
)
```

기능은 같지만, 팀이 `ramda`나 함수 합성 스타일에 익숙하지 않다면 오히려 읽기 어려워질 수 있다. 스타일 취향이 구조 개선보다 앞선 경우다.

## 불필요한 추상화는 복잡성만 늘린다

리팩터링 과정에서 클래스, 헬퍼, 레이어, 패턴을 과도하게 도입하는 경우가 있다. 그러나 단순한 로직을 억지로 객체지향 구조로 감싸거나 지나치게 많은 단계로 분리하면, 오히려 한눈에 이해하기 어려워진다.

좋은 리팩터링은 필요 최소한의 추상화만 사용한다.

### 좋은 리팩터링 예시

```js
function formatPrice(price) {
  return `$${price.toFixed(2)}`
}

function renderProduct(product) {
  return `${product.name} - ${formatPrice(product.price)}`
}
```

중복될 수 있는 가격 포맷팅만 작게 분리했다. 재사용성과 가독성이 함께 좋아진다.

### 나쁜 리팩터링 예시

```js
class PriceFormatterService {
  constructor(currencySymbolProvider) {
    this.currencySymbolProvider = currencySymbolProvider
  }

  format(price) {
    return `${this.currencySymbolProvider.getSymbol()}${price.toFixed(2)}`
  }
}

class ProductRenderer {
  constructor(priceFormatterService) {
    this.priceFormatterService = priceFormatterService
  }

  render(product) {
    return `${product.name} - ${this.priceFormatterService.format(product.price)}`
  }
}
```

복잡한 요구사항이 없는 상황에서 서비스와 의존성 주입 구조를 도입하면, 단순한 기능을 이해하는 데 불필요한 비용만 생긴다.

## 일관성은 개별 코드의 우아함보다 중요하다

팀 프로젝트에서 중요한 가치 중 하나는 일관성이다. 애플리케이션 전체가 특정 데이터 패칭 방식이나 상태 관리 방식을 사용하고 있다면, 일부 컴포넌트에서만 다른 패턴을 도입하는 것은 혼란을 만든다.

리팩터링은 개별 코드의 미적 완성도보다 전체 코드베이스의 통일성을 우선해야 한다.

### 좋은 리팩터링 예시

```jsx
function UserList() {
  const [users, setUsers] = useState([])

  useEffect(() => {
    let cancelled = false

    async function loadUsers() {
      const response = await fetch('/api/users')
      const data = await response.json()

      if (!cancelled) {
        setUsers(data)
      }
    }

    loadUsers()

    return () => {
      cancelled = true
    }
  }, [])

  return users.map((user) => <div key={user.id}>{user.name}</div>)
}
```

프로젝트 전반이 `fetch + useEffect` 패턴을 쓰고 있다면, 이 흐름 안에서 개선하는 편이 더 일관적이다.

### 나쁜 리팩터링 예시

```jsx
import useSWR from 'swr'

function UserList() {
  const { data: users = [] } = useSWR('/api/users', (url) =>
    fetch(url).then((response) => response.json())
  )

  return users.map((user) => <div key={user.id}>{user.name}</div>)
}
```

`useSWR` 자체가 나쁜 것은 아니다. 하지만 코드베이스 전체가 다른 패턴을 사용 중인데 일부만 새 라이브러리로 바꾸면 문맥이 깨지고 유지보수성이 떨어진다.

## 이해 없는 리팩터링은 위험하다

겉으로 보기에 불필요해 보이는 코드라도 실제로는 중요한 이유가 숨어 있을 수 있다. 예를 들어 단순해 보이지 않는 캐싱 로직은 성능 최적화를 위해 존재할 수 있다. 이를 충분히 이해하지 못한 채 제거하면 코드는 짧아질 수 있어도 시스템은 더 느려지고 더 많은 문제를 일으킬 수 있다.

좋은 리팩터링은 먼저 기존 코드가 무엇을 해결하고 있는지 파악한 뒤에 이루어져야 한다.

### 좋은 리팩터링 예시

```js
const userCache = new Map()

async function getUser(userId) {
  if (userCache.has(userId)) {
    return userCache.get(userId)
  }

  const user = await fetchUserFromDatabase(userId)
  userCache.set(userId, user)
  return user
}
```

코드가 조금 길어 보여도, 반복 조회 비용을 줄이기 위한 의도가 분명하다.

### 나쁜 리팩터링 예시

```js
async function getUser(userId) {
  return fetchUserFromDatabase(userId)
}
```

겉보기에는 더 단순하지만, 원래 있던 캐싱 목적을 이해하지 못하고 제거했다면 성능 회귀가 생길 수 있다.

## 기술적 우아함보다 비즈니스 맥락이 우선이다

현대적인 기술을 적용했다고 해서 항상 더 나은 리팩터링이 되는 것은 아니다. SEO가 중요한 서비스에 순수 클라이언트 사이드 렌더링 구조를 도입하면, 기술적으로는 현대적일지 몰라도 비즈니스적으로는 실패가 될 수 있다.

리팩터링은 기술 선택의 문제가 아니라, 서비스의 목표와 운영 맥락에 맞는 구조를 선택하는 문제이기도 하다.

### 좋은 리팩터링 예시

```jsx
export default async function ProductPage({ params }) {
  const product = await getProduct(params.id)

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
    </main>
  )
}
```

검색 유입이 중요한 페이지라면 서버에서 바로 콘텐츠를 렌더링하는 구조가 더 적절할 수 있다.

### 나쁜 리팩터링 예시

```jsx
'use client'

export default function ProductPage({ productId }) {
  const [product, setProduct] = useState(null)

  useEffect(() => {
    fetch(`/api/products/${productId}`)
      .then((response) => response.json())
      .then(setProduct)
  }, [productId])

  if (!product) {
    return <div>Loading...</div>
  }

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
    </main>
  )
}
```

기술적으로는 최신 프런트엔드 패턴처럼 보일 수 있어도, SEO와 초기 노출 속도가 중요한 서비스에서는 적합하지 않을 수 있다.

## 공통화는 유연성을 해치지 않아야 한다

중복 제거는 리팩터링의 대표적인 목표 중 하나다. 하지만 서로 다른 설정과 목적을 가진 코드를 하나의 추상화로 억지로 묶으면, 각 코드가 원래 갖고 있던 세부 제어 능력을 잃어버릴 수 있다.

좋은 리팩터링은 공통된 부분을 줄이되, 각 상황에 맞게 조정할 수 있는 유연성까지 함께 보존해야 한다.

### 좋은 리팩터링 예시

```js
function createRequestConfig({ timeout = 3000, retries = 0 } = {}) {
  return {
    timeout,
    retries,
    headers: {
      'Content-Type': 'application/json',
    },
  }
}

const paymentRequest = createRequestConfig({ timeout: 5000, retries: 2 })
const searchRequest = createRequestConfig({ timeout: 1000 })
```

공통 설정은 묶되, 상황별 차이는 옵션으로 열어 두었다.

### 나쁜 리팩터링 예시

```js
const defaultRequestConfig = {
  timeout: 3000,
  retries: 0,
  headers: {
    'Content-Type': 'application/json',
  },
}

const paymentRequest = defaultRequestConfig
const searchRequest = defaultRequestConfig
```

중복은 줄었지만, 결제 요청과 검색 요청처럼 성격이 다른 흐름의 차이를 표현할 수 없게 된다.

## 좋은 리팩터링의 기준

좋은 리팩터링은 보통 다음과 같은 특징을 가진다.

- 기존 동작을 유지한다.
- 코드베이스의 기존 스타일과 일관성을 지킨다.
- 복잡성을 줄이고 가독성을 높인다.
- 작고 점진적인 변경으로 진행된다.
- 충분한 이해와 테스트를 바탕으로 수행된다.

## 결론

리팩터링의 목표는 코드를 새롭게 쓰는 것이 아니라, 더 쉽게 이해하고 더 안전하게 유지보수할 수 있도록 만드는 것이다. 겉보기에 더 현대적이고 더 추상화된 코드가 반드시 더 좋은 코드는 아니다.

오히려 좋은 리팩터링은 외부 사용자에게는 거의 보이지 않지만, 개발자에게는 큰 차이를 만드는 조용한 개선에 가깝다. 결국 리팩터링에서 가장 중요한 것은 기술적 취향이 아니라, 기존 동작을 존중하고 팀과 비즈니스를 함께 고려하는 태도라고 할 수 있다.
