## 1. JWT란 무엇인가

JWT는 **JSON Web Token**의 약자이다.

서버와 클라이언트 사이에서 사용자 정보나 권한 정보를 JSON 형태로 담아 주고받기 위한 토큰 방식이다.

일반적인 JWT는 다음처럼 `.`으로 구분된 세 부분으로 구성된다.

```txt
xxxxx.yyyyy.zzzzz
```

각 부분은 다음을 의미한다.

```txt
Header.Payload.Signature
```

즉, JWT는 크게 다음 세 요소로 나뉜다.

| 구성 요소 | 의미                                           |
| --------- | ---------------------------------------------- |
| Header    | 어떤 알고리즘으로 서명했는지                   |
| Payload   | 사용자 정보, 권한, 만료 시간 등의 클레임       |
| Signature | 위 내용이 위조되지 않았는지 검증하기 위한 서명 |

JWT 공식 문서에서도 JWT는 Header, Payload, Signature 세 부분으로 구성된다고 설명한다.

## 2. JWT가 필요한 이유

HTTP는 기본적으로 **Stateless**, 즉 상태를 기억하지 않는 프로토콜이다.

예를 들어 사용자가 로그인했다고 하더라도, 다음 요청에서 서버는 그 사용자가 방금 로그인한 사용자인지 기본적으로 알 수 없다.

그래서 로그인 상태를 유지하기 위해 보통 두 가지 방식을 사용한다.

1. 세션 기반 인증
2. 토큰 기반 인증

세션 방식은 서버가 로그인 정보를 저장한다.

반면 JWT 방식은 서버가 로그인 정보를 매번 저장하지 않고, 클라이언트가 토큰을 들고 다닌다.

흐름은 보통 다음과 같다.

1. 사용자가 로그인한다.
2. 서버가 아이디/비밀번호를 검증한다.
3. 검증에 성공하면 서버가 JWT를 발급한다.
4. 클라이언트는 JWT를 저장한다.
5. 이후 요청마다 JWT를 함께 보낸다.
6. 서버는 JWT의 서명을 검증하고 사용자를 식별한다.

즉, JWT의 핵심 장점은 서버가 세션 저장소를 조회하지 않아도 토큰 자체를 검증해서 사용자를 확인할 수 있다는 점이다.

## 3. JWT 안에는 무엇이 들어가는가

JWT의 Payload에는 보통 다음과 같은 정보가 들어간다.

```json
{
  "sub": "user_123",
  "name": "홍길동",
  "role": "USER",
  "iat": 1710000000,
  "exp": 1710003600
}
```

여기서 중요한 것은 JWT의 Payload는 **암호화된 것이 아니라 인코딩된 것**이라는 점이다.

즉, 누구나 JWT 문자열을 디코딩하면 Payload 내용을 볼 수 있다.

따라서 JWT 안에는 비밀번호, 주민등록번호, 카드번호 같은 민감 정보를 넣으면 안 된다.

OWASP 역시 JWT를 테스트할 때 Payload에 민감 정보가 노출되지 않는지 확인해야 한다고 권장한다.

## 4. JWT의 장점

JWT의 장점은 명확하다.

첫째, 서버가 세션을 저장하지 않아도 된다.

서버는 토큰의 서명만 검증하면 된다. 그래서 여러 서버로 확장할 때 세션 공유 문제를 줄일 수 있다.

둘째, 토큰 안에 필요한 정보를 담을 수 있다.

예를 들어 사용자 ID, 권한, 만료 시간 등을 Payload에 넣을 수 있다.

셋째, 모바일 앱, 웹, 마이크로서비스 환경에서 사용하기 편하다.

Authorization 헤더에 담아 전달하기 쉽기 때문이다.

```http
Authorization: Bearer <access_token>
```

## 5. JWT의 가장 큰 한계

JWT의 가장 큰 한계는 **한 번 발급된 토큰을 중간에 무효화하기 어렵다는 점**이다.

세션 방식에서는 서버가 세션 저장소에서 해당 세션을 삭제하면 로그아웃 처리가 가능하다.

```txt
세션 방식:
서버 세션 삭제 -> 즉시 로그아웃 처리 가능
```

하지만 JWT는 기본적으로 토큰 자체가 유효성을 가진다.

```txt
JWT 방식:
토큰이 탈취됨 -> 만료 시간 전까지 계속 사용 가능
```

즉, 사용자가 로그아웃하더라도 이미 발급된 JWT가 만료되지 않았다면, 서버 입장에서는 그 토큰을 여전히 유효한 토큰으로 볼 수 있다.

이것이 JWT의 핵심적인 한계이다.

## 6. JWT는 "로그아웃"이 어렵다

JWT를 사용하면 로그아웃이 생각보다 단순하지 않다.

클라이언트에서 토큰을 삭제하면 되는 것처럼 보이지만, 이것은 "내 브라우저에서만 토큰을 지운 것"이다.

문제는 누군가 이미 토큰을 복사해갔다면, 그 토큰은 만료 시간까지 계속 사용될 수 있다는 것이다.

```txt
클라이언트 토큰 삭제 = 내 기기에서만 삭제
서버 측 토큰 무효화 = 별도 장치 필요
```

그래서 JWT에서 강제 로그아웃, 계정 정지, 비밀번호 변경 후 전체 로그아웃 같은 기능을 구현하려면 추가 설계가 필요하다.

예를 들면 다음과 같은 방식이다.

1. Access Token 만료 시간을 짧게 둔다.
2. Refresh Token을 별도로 운영한다.
3. 서버에 블랙리스트 또는 토큰 버전 정보를 저장한다.
4. 중요한 요청에서는 DB 상태를 다시 확인한다.

## 7. JWT는 탈취되면 위험하다

JWT는 일종의 출입증과 같다.

누군가 이 출입증을 훔치면, 서버는 그 사람이 진짜 사용자인지 아닌지 구분하기 어렵다.

서명이 유효하고 만료 시간이 지나지 않았다면 정상 요청으로 판단할 수 있기 때문이다.

그래서 JWT 저장 위치가 중요하다.

브라우저에서 많이 고민하는 저장 위치는 다음과 같다.

1. localStorage
2. sessionStorage
3. Cookie
4. Memory

`localStorage`에 저장하면 구현은 쉽지만, XSS 공격에 취약할 수 있다.

악성 스크립트가 실행되면 토큰을 읽어갈 수 있기 때문이다.

JWT 공식 소개 문서도 토큰은 자격 증명이므로 보안 문제를 막기 위해 주의해야 하며, 일반적으로 필요한 기간보다 오래 보관하지 말라고 설명한다. 또한 민감한 세션 데이터를 브라우저 저장소에 저장하지 말라고 언급한다.

## 8. JWT는 만능 인증 방식이 아니다

JWT를 처음 배우면 이런 느낌이 들 수 있다.

> 세션보다 JWT가 더 최신 방식이고 좋은 방식 아닌가?

하지만 정확히는 그렇지 않다.

JWT는 장점이 있지만, 모든 서비스에 무조건 적합한 방식은 아니다.

예를 들어 일반적인 웹 서비스에서 서버가 세션 저장소를 운영하는 데 큰 부담이 없다면, 세션 방식이 오히려 더 단순하고 안전할 수 있다.

반대로 다음과 같은 상황에서는 JWT가 유용할 수 있다.

1. 모바일 앱과 API 서버가 통신하는 경우
2. 여러 서버 또는 마이크로서비스 간 인증 정보 전달이 필요한 경우
3. 서버 간 신뢰할 수 있는 정보 교환이 필요한 경우
4. 짧은 수명의 Access Token을 사용하는 구조

## 9. 실무에서 권장되는 JWT 구조

실무에서는 보통 JWT 하나만 오래 쓰지 않는다.

대신 다음과 같이 나눈다.

```txt
Access Token  : 짧은 수명, API 요청에 사용
Refresh Token : 긴 수명, Access Token 재발급에 사용
```

예를 들면 다음과 같다.

```txt
Access Token 만료 시간  : 10분 ~ 30분
Refresh Token 만료 시간 : 며칠 ~ 몇 주
```

Access Token이 탈취되더라도 짧은 시간 후 만료되도록 하고, Refresh Token은 서버에서 관리하거나 회전 전략을 사용한다.

```txt
로그인
 -> Access Token 발급
 -> Refresh Token 발급

API 요청
 -> Access Token 사용

Access Token 만료
 -> Refresh Token으로 재발급 요청

Refresh Token 이상 감지
 -> 재로그인 요구
```

## 10. 결론

JWT는 "로그인 상태를 유지하기 위한 토큰"으로 자주 사용되지만, 본질은 **서명된 JSON 기반 클레임 전달 형식**이다.

핵심은 다음과 같다.

1. JWT는 서버가 발급한 서명된 토큰이다.
2. Payload는 누구나 볼 수 있으므로 민감 정보를 넣으면 안 된다.
3. 서명은 위조 여부를 확인하기 위한 장치이다.
4. JWT는 Stateless 인증에 유리하다.
5. 하지만 한 번 발급된 토큰을 즉시 무효화하기 어렵다.
6. 탈취되면 만료 전까지 악용될 수 있다.
7. 그래서 짧은 Access Token과 Refresh Token 구조가 자주 사용된다.

정리하면 JWT는 나쁜 기술이 아니다.

다만 "세션보다 무조건 좋은 최신 인증 방식"도 아니다.

JWT는 서버 확장성, API 인증, 모바일/마이크로서비스 환경에서는 강력한 도구가 될 수 있다.

하지만 로그아웃, 토큰 탈취, 강제 무효화, 저장 위치 보안까지 함께 설계하지 않으면 오히려 위험해질 수 있다.
